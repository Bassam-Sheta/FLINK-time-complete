## Changes implemented and locally tested

Severity describes the pre-change risk, not a claim of a demonstrated production exploit.

| Priority | Issue and impact | Implementation | Evidence |
|---|---|---|---|
| High | App passwords used 10,000 PBKDF2 iterations; stronger hashing had no Google runtime benchmark | User-selected Google primary identity with mandatory app TOTP MFA. No app password validation or hashing in the Google mode; old hashes are retired on sign-in; new accounts store no app password | Google authentication tests; legacy password tests explicitly exercise the disabled compatibility path |
| High | Initial enrollment could otherwise grant access before MFA completion | Enrollment-only sessions; default-deny API restriction allows validation, enrollment, confirmation, and logout only. MFA grants are server-side, user/session-bound, and expire | Authentication boundary and session-rotation tests |
| High | Unbounded administrative password/MFA retries and concurrent replay opportunities | Script-lock serialization and persistent per-user limit of 10 reauthentication attempts per 15 minutes, including enrollment and confirmation; malformed limiter state fails closed | Reauthentication-limit tests and existing TOTP replay tests; actual Google lock behavior untested |
| High | Employee weekly timesheets exposed immutable financial entry snapshots | Public timesheet headers omit `EntrySnapshotJSON` and internal row indices; stored approval snapshots remain intact | Timesheet integrity and financial-privacy tests |
| High | Lifecycle queue could store credentials or execute injected privilege/workspace fields | Bounded allowlist for request data, explicit user-provisioning fields, server-controlled role/workspace, redaction of legacy queued data in responses | Request security and workflow tests |
| Medium | MFA secrets used bespoke encryption | Pinned TweetNaCl 1.0.3 XSalsa20-Poly1305 for new secrets; strict ciphertext parsing; v1 decrypt compatibility; upgrade of stored legacy secrets during Google sign-in | Round-trip, tampering, wrong-key, legacy-fixture and V8-adapter tests |
| Medium | UUID fixed version/variant bits were counted as random data | Remove both nibbles, concatenate validated UUIDv4 random portions, validate byte counts and fail closed on incompatible output | Local fallback tests. | Medium | Configured idle timeout was ignored | Strict configuration read; 1–24-hour validated bound applied to session creation and validation | Configured-timeout test |
| Medium | Auto-stop setting was ignored and long timer end/duration could disagree | Configured cutoff sets both duration and end timestamp; owner trigger sweeps every five minutes; deterministic entry identity makes repeated stops harmless | Timer sweep and retry tests; trigger execution untested in Google |
| Medium | Closed metadata could strand an existing running timer | Existing unchanged timer assignments can finalize; new assignments still require active metadata and access | Tracking policy paths reviewed; full Google workflow remains untested |

| Medium | Installer failures could imply cleanup succeeded or misclassify all authorization failures | Return actual cleanup result and incomplete-sheet link; distinguish expired authorization, denied permissions, and disabled API access | Installer source checks and tests; real Google API installation remains untested |
| Low | Reserved report-group names could collide with object properties | Null-prototype grouping dictionaries | Reserved-name report tests |
| Low | Duplicated portals/backend made security fixes drift | Ordered backend modules plus one shared GUI template and role fragments; deterministic generation with stale-output gate | Build check, backend parsing, portal tests |

## Ordered completion plan

1. **Publish and verify the repository.** Publication and CI on implementation commit `96932f6` are observed. Record CI again after subsequent changes; keep the installer pinned to an immutable runtime commit. The original repository is unchanged.
2. **Prepare an isolated Google installation.** Source backup, disposable private Master Sheet binding, and five-file persistence comparisons are observed. Next obtain action-time approval for the configured domain-only, execute-as-owner deployment and any Google OAuth consent. Have the owner enroll their own authenticator; never expose its secret in an issue or report.
3. **Verify installation against Google.** Run both first installation and interrupted/retried installation; confirm the source pin, bootstrap-owner checks, schema initialization, actual cleanup, deployment URLs, and required OAuth scopes. Test cleanup denial and API-policy denial. Add resumable installer state if retries create duplicate systems; current installer has no persistent resume checkpoint.
4. **Verify authentication with real accounts.** Use separate owner, manager, employee, unrelated-domain, and unassigned accounts. Check absent Google identity, duplicate legacy email accounts, active/inactive/timed-lock states, no-MFA restrictions, enrollment replacement, challenge expiration/reuse, wrong codes, limiter behavior, session epoch revocation, and identity switching. Verify both direct portals and employee Google Sites embedding. Root authenticator recovery needs a documented owner-only recovery procedure; generic web recovery intentionally cannot disable root MFA.
5. **Verify access control and privacy.** Call all API actions directly outside the GUI. Confirm role and workspace rejection, employee user-ID substitution resistance, no employee financial snapshots, manager request constraints, cross-workspace request visibility, root invariants, GET restrictions, sanitized errors, and fresh step-up enforcement for every high-risk action.
6. **Verify concurrency, timers, and payroll data.** Run concurrent timer starts/stops, duplicate retries, shutdowns, closed projects/tasks/tags, user deactivation, and timed sweeps with real ScriptLock. Confirm actual 5-minute trigger installation and execution. Inspect multi-day timer allocation: the configured maximum is 168 hours, while existing report/rollup conventions assign entries to a business date. Decide and implement day-by-day allocation before enabling multi-day payroll use. Deleted tracking metadata requires repair rather than invented rate snapshots.
7. **Verify data integrity and recovery.** Submit/approve/reject/reopen timesheets, confirm rate snapshots and audit-chain/checkpoint behavior, create/verify/restore Drive backups, test denied Drive access and failed rollup reconciliation, and confirm workspace pointer changes only after restore success. Check retention, file ownership, sharing, and backup protection in Google.
8. **Verify quotas and scale.** Measure real request count/latency, timer sweeps, Script Properties storage, Sheets growth, and Drive backup costs. MFA grants add one Script Property per verified session until expiry cleanup; validate capacity at expected concurrent-user counts. Add admission control or move grant storage if the real quota is approached. Limit batches to measured Apps Script execution time.
9. **Finish functional edge cases.** `PROFILE_CHANGE` and `OTHER` request types remain non-executable in the inherited workflow; define approval semantics and implement them if they are exposed for operational use. Check keyboard access, narrow screens, error recovery, installer retry UX, all settings, exports, and all role-specific controls with real data.
10. **Release after live evidence.** Record exact deployment version, source SHA, test accounts/roles, observed timestamps, failures and repairs. Repeat only affected tests after changes. Do not call the app production-ready or all security issues fixed until these target-environment checks pass.

## Platform references

Google identity depends on server-observed active-user email. In execute-as-owner deployments, Google documents identity restrictions and a same-Workspace-domain exception: [Session](https://developers.google.com/apps-script/reference/base/session). The app fails closed when email is unavailable.

Google documents `getUuid()` as equivalent to Java `UUID.randomUUID()`: [Utilities](https://developers.google.com/apps-script/reference/utilities/utilities.html). Java documents a cryptographically strong PRNG for that method: [UUID](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/UUID.html). Local tests cannot establish the entropy of Google's live implementation.

Bundled library source: TweetNaCl 1.0.3, unmodified `nacl-fast.min.js`, SHA-256 `3ec535c004aeeb225785d8e93fb33bf99f52e399bd7dfc01969b5629baea5131`. The license is under `vendor/tweetnacl-1.0.3/LICENSE`. No remote crypto script is loaded by the app.
